# 의뢰서 B-05: 보존 메타데이터 표준 조사

넘길 때 [의뢰서 모음](crate::docs::briefs)의 **공통 규칙과 공통 보고 형식**을 같이 넘긴다. 작성 기준일은 2026-10-08이다.
이 의뢰서는 **제안을 허용한다**(공통 규칙 9). 결정은 사용자가 한다.

## 1. 배경과 방침

- 프로젝트: `chicken_manu`(치킨메뉴). 리듬게임·음악게임의 **매체**(채보 등 플레이를 규정하는 데이터)와 매체가 참조하는 **에셋**(음원, 이미지, 영상 등)을
  도서관의 목록처럼 관리하고 서로 공유하는 Rust 도구를 만든다.
- **방침(사용자)**: 메타데이터 형식을 직접 만들고 계속 고치는 일은 감당하기 어렵다. 그래서 **기존 표준을 따르고 활용한다.**
  로드맵의 원래 문구는 "METS에서 파생시켜서 메타데이터에 대한 스키마를 직접 최신화하는 부분을 줄임. XML과 인코딩은 UTF-8로."이다.
  - 즉 목표는 **표준이 이미 정한 것을 최대한 그대로 쓰고, 표준에 없는 이 프로젝트 고유의 부분만 최소한으로 덧붙이는 것**이다.
- 이 조사의 질문: **매체와 에셋을 "보존"하려면 어떤 메타데이터가 필요한가.** 그리고 그것을 어떤 표준의 어떤 요소에 담을 것인가.

## 2. 이미 알려진 것 (다시 조사하지 말고 검증만)

아래는 이 프로젝트의 기존 문서([기술 채택 판단](crate::docs::adoption), [참고 자료](crate::docs::references), [스키마와 식별자](crate::docs::schema))에 적힌 값이다.
**모두 2026-10-08 시점의 값이며 재확인 대상이다.** 어긋나면 어긋남을 적는다.

| 항목 | 기존 기록 | 상태 |
| --- | --- | --- |
| METS 1.12.1 | `CHECKSUMTYPE`이 11개 값의 닫힌 열거형이라 SHA-3을 넣을 수 없다 | 확인(원문 XSD) |
| METS 2 | `v2/mets2.xsd`, Version 2.0, 2025년 3월. `CHECKSUMTYPE`이 자유 문자열이고 제안 값 위키에는 11개뿐이다. "다른 값은 각 profile이 해석한다" | 확인(XSD, 위키). profile 문서·예제·마이그레이션 노트·도구는 **읽지 못함** |
| METS-schema 저장소 | 릴리스·태그 없음, LICENSE 파일 없음, 마지막 커밋 2025-03-12 | 확인 |
| PREMIS 3.0 | 해시 함수 어휘 13개 항에 SHA3·BLAKE가 없다 | 확인 |
| MODS, DCMI Terms, MIX | 제목·아티스트 등 기술(descriptive) 메타데이터와 이미지 기술 메타데이터 후보 | 확인(주소만) |
| `docs/schema.md` 3절 | 이 프로젝트의 DB 컬럼과 METS 요소의 대응 초안. `dmdSec`에 MODS 또는 Dublin Core를 담는 안 포함 | **제안, 미검증** |
| RO-Crate, BagIt, OCFL | 대안 비교는 2차 정보만 있어 제외했다 | **미조사** |

## 3. 요청

1. **보존 메타데이터의 필요 항목을 표준에서 도출**한다. 항목을 이 프로젝트가 만들어 내지 않고, 표준의 요소 이름과 정의를 그대로 가져온다.
2. 그 항목을 **METS(1.12.1과 2)의 어느 섹션에 담는지** 정리한다.
3. 같은 일을 하는 **대안 표준**(RO-Crate, BagIt, OCFL 등)을 1차 출처로 비교한다.
4. 표준으로 덮이지 않는 **이 프로젝트 고유의 부분**(갭)을 찾아, 최소한의 확장 목록으로 정리한다.
5. 위를 바탕으로 **최소 프로파일 초안**을 `[제안]`으로 낸다.

## 4. 조사할 표준 (시작점)

아래 목록과 요소 이름은 작성자의 기억이므로 **존재와 내용을 먼저 확인**한다.

| 구분 | 후보 | 확인할 것 |
| --- | --- | --- |
| 구조 | METS 1.12.1, METS 2 | `dmdSec`, `amdSec`(`techMD`, `rightsMD`, `sourceMD`, `digiprovMD`), `fileSec`, `structMap`, `structLink`, `behaviorSec`의 역할. 두 버전의 차이와 현행 권장 |
| 보존 | PREMIS 3 | Object, Event, Agent, Rights 엔티티와 요소. **fixity**(체크섬)·**원본 이름·위치**·**이벤트(수집, 검증, 변환)**의 표현 |
| 참조 모델 | OAIS(ISO 14721) | SIP, AIP, DIP와 "보존 기술 정보(PDI)"의 구분(참조, 맥락, 출처, 불변성, 접근 권리) |
| 기술(descriptive) | MODS, Dublin Core(DCMI Terms) | 곡명, 제작자, 장르, 부제 등을 담는 요소. 제작 참여자(명의)의 표현 |
| 기술(technical) | MIX(이미지), 오디오·영상용 표준(AES57, PBCore 등), textMD | 에셋 종류별 기술 메타데이터가 표준에 있는가. 없으면 없다고 적는다 |
| 패키징 | BagIt, OCFL, RO-Crate | 묶음의 구조, 체크섬 매니페스트, 버전 관리. METS와의 관계(대체인가 보완인가) |
| 식별 | multihash/multicodec, CID, IANA 해시 이름 | 해시 알고리즘 이름 철자와 코드. SHA3-256, BLAKE3를 표준이 어떻게 부르는가 |
| 단계 기준 | NDSA Levels of Digital Preservation | [B-04](crate::docs::briefs::preservation_p2p)가 다룬다. 중복 조사를 피하고 결과만 이어 쓴다 |

## 5. 대상마다 답해야 할 질문

각 답에 **근거**(표준 문서의 구절과 위치, 요소 이름)와 확인 상태, 신빙성을 붙인다.

| 번호 | 질문 |
| --- | --- |
| S1 | 보존에 필요한 메타데이터를 표준들은 어떤 **범주**로 나누는가(예: 기술, 구조, 관리, 출처, 권리). 각 범주의 요소 목록과 정의(짧은 인용) |
| S2 | **무결성 검증(fixity)**에 필요한 최소 항목은 무엇인가(알고리즘, 값, 계산 대상 바이트, 검사 이력). PREMIS와 METS에서 각각 어디에 담는가 |
| S3 | **출처와 이력**(어디서 왔고 누가 무엇을 했는가)을 담는 표준 요소. 이 프로젝트의 "제작 참여자(명의)"와 대응하는 것 |
| S4 | **원래 이름과 위치**를 보존하는 방법. 매체가 `#WAV01 kick.wav`처럼 에셋을 파일명으로 참조할 때, 그 참조 문자열과 실제 파일의 관계를 담는 표준 요소가 있는가 |
| S5 | **권리·라이선스**를 담는 요소(`rightsMD`, PREMIS Rights 등)와 외부 어휘. 저작권 조사는 [B-03](crate::docs::briefs::copyright)이 다루므로 여기서는 **담는 자리**만 본다 |
| S6 | 한 매체가 여러 에셋을 참조하는 **구조 관계**를 METS `structMap`/`structLink`로 표현하는 표준적인 방법과 사례 |
| S7 | **METS 2**의 profile 작성 방법. 필수·선택 요소를 어떻게 선언하고, 해시 이름 같은 자유 문자열 값의 철자를 profile이 어떻게 정하는가. 공개된 profile과 예제 |
| S8 | METS 1.12.1을 쓸 때와 METS 2를 쓸 때 **SHA3-256, BLAKE3**를 담는 방법의 차이. 현행 권장과 도구 지원 현황(검증기, 라이브러리) |
| S9 | BagIt, OCFL, RO-Crate가 S1~S6을 어떻게 다루는가. METS와 **병용**하는 사례가 있는가. 이 프로젝트의 "목록(카탈로그)을 서로 공유" 목표에 어느 쪽이 맞는가는 평가하지 말고 사실만 |
| S10 | 표준이 덮지 않는 **게임 매체 고유 정보**: 시간 기저(마디 격자, 틱, 절대 시간), 채보 단위(한 파일에 난이도가 몇 개), 난이도, 키 수, 모드. 기존 표준에 이런 요소가 있는가. 없다면 가장 가까운 확장 지점(예: METS `xmlData` 안의 자체 네임스페이스)은 무엇인가 |

## 6. 산출물

`docs/` 아래에 넣을 마크다운 문서로 낸다.

1. **표준 목록표**: 이름, 버전, 발행 기관, 주소, 라이선스, 현행 여부, 확인 상태, 신빙성, 확인일.
2. **보존 메타데이터 항목표**: 항목, 범주, 정의, 출처 표준과 요소 이름, 필요성(필수/권장/선택, 근거), 이 프로젝트의 대응 개념(묶음, 패턴, 파일, 명의, 식별, 파일 참조).
3. **갭 목록**: 표준으로 덮이지 않는 항목과 가장 가까운 확장 지점. 직접 정의해야 하는 것을 **최소**로 줄인 목록.
4. **`docs/schema.md` 3절의 METS 대응 초안 검증**: 맞는 줄, 틀린 줄, 고칠 줄. 틀린 요소 이름이나 위치를 찾으면 정정안을 낸다.
5. `[제안]` **최소 프로파일 초안**: UTF-8 XML 예시 한 개. 실제 스키마 파일(XSD)로 검증했는지, 검증 도구와 결과를 적는다. 검증하지 못했으면 `미검증`이라고 쓴다.
6. 열린 질문: 표준만으로는 정할 수 없어 사용자가 정해야 하는 것.

## 7. 하지 말 것

- 요소 이름, 네임스페이스, 버전을 기억으로 채우지 않는다. 확인한 것만 적고 나머지는 `미확인`이다.
- 표준의 스키마·사양 문서를 대량으로 옮기지 않는다. 요소 이름과 짧은 인용, 위치만 적는다.
- 이 프로젝트가 새 요소나 속성을 만드는 안을 기본으로 삼지 않는다. 표준 요소로 담을 수 없다는 근거가 있을 때만 `[제안]`으로 쓴다.
- 표준끼리 우열을 매기거나 추천하지 않는다(사실 나열, 추천은 `[제안]`으로만).
- 내려받은 도구를 실행하지 않는다. XSD 검증처럼 문서와 스키마를 읽는 범위의 도구 사용은 어떤 도구를 어떻게 썼는지 적는다.
