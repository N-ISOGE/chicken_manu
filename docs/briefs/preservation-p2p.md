# 의뢰서 B-04: 보존 수준과 p2p 열람

넘길 때 [의뢰서 모음](crate::docs::briefs)의 **공통 규칙과 공통 보고 형식**을 같이 넘긴다. 작성 기준일은 2026-10-08이다.
이 의뢰서는 **제안을 허용한다**(공통 규칙 9). 결정은 사용자가 한다.

## 1. 배경

- 프로젝트: `chicken_manu`(치킨메뉴). 리듬게임·음악게임의 **매체**(채보 등)와 매체가 참조하는 **에셋**(음원, 이미지, 영상 등)을
  도서관의 목록처럼 관리하고 서로 공유하는 Rust 도구를 만든다.
- 사용자가 밝힌 방향:
  - 공유는 처음에 **Rust의 libp2p로 IPFS**를 쓰려고 했다. 기술 채택을 위한 조사가 더 필요하다.
  - 보존의 수준은 구체적으로 봐야 하지만, 일단 **p2p망을 전제**로 하고 **"열람만" 가능하게 할 수 있는지**를 묻고 있다.
- 지금까지의 조사: [기술 채택 판단](crate::docs::adoption)(kubo, iroh, rust-libp2p, 순수 Rust CID 계산 등)과 [참고 자료](crate::docs::references).
  그 문서의 내용은 **2026-10-08 시점의 값이며 다시 확인해야 한다.** 어긋나면 어긋남을 적는다.
  특히 kubo/Boxo의 유지보수 종료 위험(같은 문서 2절)과, rust-libp2p 0.57.0에 Bitswap이 없다는 기록이 이 의뢰서와 직접 관련된다.

## 2. 요청

1. "열람만 가능하다"는 말이 무엇을 뜻할 수 있는지 **해석별로 나누고**, p2p망(IPFS/libp2p 계열)에서 각 해석이 **가능한지** 조사한다.
2. 도서관식 목록 관리에 알맞은 **보존 수준의 기준**을 기존 틀에서 찾아 후보로 제안한다.
3. libp2p를 Rust에서 **직접 쓰는 방식**의 가능성과 한계를 조사한다.

## 3. "열람만"의 해석

아래 해석별 **가설은 작성자의 일반 지식이며 검증되지 않았다.** 맞는지 확인하는 것이 이 의뢰서의 핵심이다.

| 해석 | 뜻 | 작성자의 가설 (검증 대상) |
| --- | --- | --- |
| A. 수정 불가 | 받은 사람이 목록이나 파일을 바꿔서 같은 이름으로 퍼뜨릴 수 없다 | 내용 주소(CID)는 내용이 바뀌면 달라지므로 가능해 보인다. 갱신 권한은 서명 키를 가진 쪽만 갖는 구조(IPNS 등)가 있는지 확인 |
| B. 목록만 열람 | 카탈로그(메타데이터와 CID)는 보되, 에셋 본문은 따로 받아야 한다 | 목록만 공유하고 본문은 요청할 때만 받는 구조는 가능해 보인다 |
| C. 보되 사본은 남지 않음 | 파일을 열람하지만 받은 쪽에 복사본이 남지 않는다 | 파일을 받아서 보는 이상 사본을 막는 것은 일반적으로 불가능하다고 알고 있다. 이 인식이 맞는지, 예외가 있는지 |
| D. 허가된 사람만 | 정해진 상대에게만 본문을 보여 준다 | 비공개 네트워크(swarm key), 연결 허용 목록, 암호화 후 키 전달 같은 방법이 있는 것으로 기억한다. 방법별 한계를 확인 |

## 4. 대상마다 답해야 할 질문

각 답에 **근거**(공식 문서 구절, 명세, 소스 파일과 함수명)와 확인 상태, 신빙성을 붙인다.

| 번호 | 질문 |
| --- | --- |
| P1 | IPFS에서 CID를 아는 누구든 내용을 받을 수 있는가. 특정 피어만 받게 하는 **기본 기능**이 있는가(비공개 네트워크, 요청 제한 등) |
| P2 | **갱신 권한**: 목록처럼 바뀌는 데이터를 게시하고 갱신하는 방법(IPNS, 서명된 레코드, IPLD 등)과 그 권한 모델. 해석 A에 해당 |
| P3 | **암호화** 방식: 파일을 암호화해서 CID로 공유하고 키를 따로 전달하는 사례와 한계. 해석 D에 해당 |
| P4 | rust-libp2p에서 **연결 허용 목록**(connection gater 등)이나 피어 인증을 구현하는 방법과 근거 |
| P5 | iroh에서 같은 일(접근 제한, 갱신 권한)은 어떻게 하는가. iroh-blobs와 CID의 비호환 문제([기술 채택 판단](crate::docs::adoption) 참조)를 포함해 확인 |
| P6 | **가용성**: p2p망에서 파일이 계속 받아질 수 있게 하는 방법(pin, 복제, 피어 수)과 한계. 모든 노드가 내리면 어떻게 되는가 |
| P7 | **삭제와 철회**: 한 번 퍼진 CID를 거둬들일 수 있는가. 노드 단위로 막는 방법. (저작권 쪽 쟁점은 [B-03](crate::docs::briefs::copyright)이 다루므로 여기서는 **기술적으로 가능한가**만 본다) |
| P8 | rust-libp2p를 **직접** 써서 IPFS와 호환되는 노드를 만드는 데 필요한 구성(Kademlia, Bitswap, identify 등)과 현재 구현 상태. 방치된 크레이트는 방치로 기록 |
| P9 | **kubo 사이드카 방식**과 **libp2p 직접 방식**을 같은 항목으로 비교한 표(유지 상태, 라이선스, 호환성, 접근 제한 기능). 평가가 아니라 사실의 나열 |

## 5. 보존 수준의 기준

프로젝트는 "도서관처럼 목록으로 관리"하는 것을 목표로 한다. 아래는 **찾아볼 단서이며 검증 대상**이다(작성자의 기억).

| 단서 | 확인할 것 |
| --- | --- |
| NDSA Levels of Digital Preservation | 단계의 이름과 항목(저장, 무결성, 통제, 메타데이터, 내용 등), 최신 판. 이 프로젝트의 "원본 보관과 식별" 원칙이 어느 단계에 해당하는가 |
| OAIS 참조 모델(ISO 14721) | 보존 정보 패키지(SIP, AIP, DIP)와 이 프로젝트의 "묶음"의 관계 |
| PREMIS | 보존 메타데이터 항목. 이 프로젝트의 METS 파생 스키마에 넣을 항목의 후보 |
| BagIt | 파일 묶음과 체크섬을 담는 단순한 방식. 이 프로젝트의 "묶음"과 비교 |
| fixity 검사 | 파일이 변하지 않았는지 주기적으로 확인하는 관행 |

- 위 틀에서 "열람용 정규화 사본을 만들지"를 정하는 데 도움이 되는 기준이 있으면 `[제안]`으로 쓴다.
- 이 프로젝트의 원칙은 **원본을 바꾸지 않고, 디코딩 전의 원시 바이트로 식별한다**는 것이다. 이 원칙과 충돌하는 틀이 있으면 충돌을 적는다.

## 6. 산출물

`docs/` 아래에 넣을 마크다운 문서로 낸다.

1. 해석별 가능 여부 표: A~D × (가능 / 조건부 / 불가 / 미확인), 조건, 근거, 확인 상태.
2. P1~P9의 답과 근거.
3. 보존 수준 기준표: 틀별로 단계, 항목, 이 프로젝트와의 대응. `[제안]`으로 후보 수준을 몇 가지.
4. 기술 비교표(P9)와, 기술 채택 판단 문서와 **어긋난 사실**의 목록.
5. 열린 질문과 사용자가 정해야 할 것.

## 7. 하지 말 것

- 가설을 사실처럼 옮기지 않는다. 확인하지 못한 가설은 `미확인`으로 둔다.
- "가능하다"는 말을 근거 없이 쓰지 않는다. 문서에 기능이 있다는 것과 실제로 동작한다는 것을 구분한다(후자는 직접 실험하지 않았으면 `미확인`).
- 접근 제한 기능을 DRM(복제 방지)처럼 설명하지 않는다. 막을 수 있는 것과 막을 수 없는 것을 구분해서 쓴다.
- 평가나 추천("이 방식이 더 낫다")은 `[제안]`으로만 쓴다.
