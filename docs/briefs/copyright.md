# 의뢰서 B-03: 저작권과 재배포

넘길 때 [의뢰서 모음](crate::docs::briefs)의 **공통 규칙과 공통 보고 형식**을 같이 넘긴다. 작성 기준일은 2026-10-08이다.
이 의뢰서는 **사실 수집이 중심**이다. **법률 자문이 아니다.** "합법"이나 "불법"이라는 결론을 쓰지 말고, 근거와 불확실한 점을 쓴다.

## 1. 배경

- 프로젝트: `chicken_manu`(치킨메뉴). 리듬게임·음악게임의 **매체**(채보 등 플레이를 규정하는 데이터)를 도서관의 목록처럼 관리하고 서로 공유하는 도구를 만든다.
- 용어: **에셋**은 매체가 참조하는 파일(음원, 키음, 이미지, 영상 등)이다. 매체에 속하지 않는다.
- 도구가 하려는 일(전부 계획이며 구현은 아직 없다):
  1. 매체와 에셋을 읽어 **메타데이터**(곡명, 제작자, 파일 목록 등)를 뽑는다.
  2. 파일의 **해시와 IPFS CID**를 계산해 기록한다.
  3. 그 **목록(카탈로그)**을 서로 공유한다.
  4. 가능하면 매체와 에셋 **파일 자체**를 p2p망으로 주고받는다(방식은 미정이고 [기술 채택 판단](crate::docs::adoption)에서 조사 중).
- 이전 조사에서 **조사하지 못한 항목**: 곡·그림·영상의 배포 조건, 행사별 약관, 삭제 요청 처리.
- 이 프로젝트가 정하려는 것: 도구가 어디까지 책임질지, 설계에 어떤 요구사항이 생기는지.

## 2. 요청

위 1~4의 **행위마다** 어떤 법적 쟁점이 있는지, 그리고 이 분야 관행이 무엇인지를 근거와 함께 조사한다.

## 3. 대상 관할

사용자는 한국어를 쓰고, BMS 생태계의 제작자와 사이트는 일본 쪽이 많다고 알려져 있다(검증 대상). 따라서 시작점은 다음과 같다.

| 우선 | 관할 | 이유 |
| --- | --- | --- |
| P1 | 대한민국 | 도구 개발자의 소재지 |
| P1 | 일본 | 매체 제작자와 배포처의 다수 |
| P2 | 미국 | 호스팅·서비스 사업자 다수, 면책 제도 비교 |
| P3 | EU | 필요하면 |

어느 관할을 다뤘고 어느 관할을 다루지 못했는지 보고에 쓴다. 관할을 추가하는 것은 `[제안]`으로 쓴다.

## 4. 대상마다 답해야 할 질문

각 답에 **근거**(법령 조문, 판례, 공식 지침, 약관 구절)와 확인 상태, 신빙성을 붙인다.

| 번호 | 질문 |
| --- | --- |
| C1 | 곡명, 제작자명, 장르, BPM, 파일 해시 같은 **사실 정보의 메타데이터**를 뽑아 공유하는 행위는 저작물의 복제·전송에 해당하는가. 보호받는 부분과 아닌 부분의 기준 |
| C2 | **채보 자체**(타이밍과 배치를 적은 데이터)는 저작물로 보호받는가. 음원에 대한 2차적 저작물이 되는가. 논의가 있으면 출처와 함께 |
| C3 | **링크, 해시, CID만 공유**하는 목록은 침해 쟁점에서 어떻게 다뤄지는가(링크·색인 제공 행위에 관한 법령과 판례) |
| C4 | p2p망에서 **파일을 받아 보관하고 다시 내보내는 노드**(IPFS의 pin과 Bitswap 등)의 행위는 복제·전송으로 보는가. 노드 운영자의 책임 |
| C5 | IPFS 같은 **내용 주소 기반 망의 삭제 요청** 처리 관행. 네트워크에서 지울 수 없을 때 노드 단위로 막는 방법이 있는가(차단 목록 등) |
| C6 | BMS 계열 생태계의 **배포 관행**: 제작자가 파일에 적는 배포 조건, 행사(이벤트) 규약, 배포 사이트 약관, 재배포 금지 표기가 있는가. 대표 사례를 출처와 함께 |
| C7 | 그 밖의 계열(StepMania, osu!, Clone Hero 계열)의 **공식 약관과 커뮤니티 관행**: 사용자 제작 채보의 권리, 상업곡 사용 조건 |
| C8 | 메타데이터에 **권리 정보와 라이선스**를 담는 기존 표준과 어휘. 단서: METS의 rights 관련 요소, PREMIS의 권리 정보, SPDX 라이선스 식별자, Creative Commons의 기계 판독 표기, RightsStatements.org. (작성자의 기억이므로 존재와 내용을 확인할 것) |
| C9 | 도서관·아카이브가 저작권 아래에서 **보존 목적으로 하는 복제**에 관한 예외 규정(한국, 일본, 미국). 개인이나 비영리 아카이브에도 적용되는지 |
| C10 | 사용자가 올린 파일에 대해 도구 제작자가 지는 책임을 줄이는 **일반적인 설계 관행**(신고 절차, 업로드 동의 문구, 권리 정보 필수 입력 등). 근거와 함께 |

## 5. 산출물

`docs/` 아래에 넣을 마크다운 문서로 낸다.

1. 관할별 요약표: 행위(1~4) × 쟁점, 근거, 확인 상태, 신빙성, 확인일.
2. 관행 조사표: 계열·사이트·행사별 배포 조건(C6, C7).
3. 권리 정보 표준표(C8): 이름, 제공 기관, 용도, 메타데이터 스키마에 담을 수 있는지.
4. 설계 요구사항 후보 `[제안]`: 예) "에셋마다 라이선스 필드를 둔다", "삭제 요청을 받는 절차를 둔다". 근거와 함께.
5. 불확실한 점의 목록: 조문만으로 정할 수 없는 것, **전문가(변호사) 확인이 필요한 것**.

## 6. 하지 말 것

- 법률 자문처럼 쓰지 않는다. 결론 대신 근거와 불확실성을 쓴다.
- 한 관할의 규칙을 다른 관할에 그대로 적용하지 않는다.
- 법령은 원문(공식 법령 사이트)을 확인한다. 블로그의 해설만으로 쓴 값은 `부분`으로 둔다.
- 약관과 라이선스 전문을 대량으로 옮기지 않는다. 구절과 위치만 적는다.
- 실제 저작물을 내려받아 확인하지 않는다.
