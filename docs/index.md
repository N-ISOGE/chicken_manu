# chicken_manu (치킨메뉴)

리듬게임·음악게임의 **매체**(채보와 그에 딸린 자산)가 어떤 형식으로 존재하는지 조사하고,
그 매체를 **공유하고 보존**하기 위한 데이터 포맷, 스키마, 도구를 명세하고 구현한다.

## 목표

목표는 두 축이다. 두 축은 서로를 먹여 살린다.

### 1. 매체의 형식 조사

리듬게임·음악게임이 플레이를 규정하는 데이터(chart, 譜面, 보면, beatmap, simfile, level 등)를
어떤 형식으로 쓰는지 **목록화하고 근거와 함께 기록**한다.

- 대상: BMS 계열, 기타 히어로 계열(`.chart`, `.mid`), osu!(`.osu`), StepMania(`.sm`, `.ssc`)를 비롯한 채보 전반과,
  이를 읽고 쓰는 구동기·에디터·파서, 그 형식을 설명하는 규격.
- 산출물: 포맷·명세 원장, 구현별 세부 문서, 비교표, 이론 문헌 목록.
- 방식: 평가나 통합에 앞서 **무엇이 존재하는지부터** 빠짐없이 기록한다. 출처마다 신빙성을 매기고 원어를 그대로 보존한다.
- 현황: BMS 계열이 가장 깊이 조사돼 있다. 다른 계열은 원장에 주소와 평가만 있다.

### 2. 공유·보존 도구의 명세와 구현

조사한 매체를 **잃지 않고 옮기고 찾을 수 있게** 하는 규칙과 도구를 만든다.

- 명세: 매체를 한 묶음으로 설명하는 메타데이터 스키마와 데이터 포맷.
  묶음(binder), 패턴(채보), 파일, 제작 참여자(명의), 파일 식별(해시, IPFS CID), 파일 참조를 다룬다.
  로드맵상 METS에서 파생한 UTF-8 XML 스키마를 목표로 한다.
- 구현: Rust 기반 도구. 채보 파일을 읽어 메타데이터와 파일 참조를 뽑고, 해시와 CID를 계산해 기록하고, 묶음을 관리·공유·배포한다.
- 현황: MariaDB 스키마 설계서 2차(2024-12-19), BMS 문법 초안, 기술 채택 사전 조사까지 했다.
  BMS 파일 읽기와 해시·CID 계산의 초기 구현은 다른 브랜치(`util-for-parsing`)에 있다.

### 두 축의 관계

- 1축의 결과가 2축의 **요구사항**이 된다. 어떤 포맷을 최소한 지원할지, 파일 참조를 어떻게 해석할지,
  채보 하나가 파일 하나인지 여러 개인지가 스키마를 정한다.
- 2축의 필요가 1축의 **조사 질문**을 정한다. 지침의 질문(파일 참조, 경로, 인코딩, 채보 단위, 묶음 단위, 식별)이
  스키마에 필요한 것들이다.
- 이 순서가 깨지지 않도록, 포맷을 스키마에 넣기 전에 해당 포맷의 세부 문서가 먼저 있어야 한다.

## 원칙

1. **원문을 기준으로 반영한다.** 출처의 표기와 용어를 그대로 두고, 통일이나 대응은 따로 기록한다.
2. **근거 없이 쓰지 않는다.** 확인하지 못한 값은 `미확인`으로 두고, 신빙성(A/B/C/X)과 확인 상태를 분리해 적는다.
3. **원본을 바꾸지 않는다.** 식별은 디코딩 전의 원시 바이트에서 계산한 해시로 한다.
4. **재현할 수 있어야 한다.** 같은 입력이 같은 식별자를 만들도록, 해시 알고리즘과 CID 생성 프로파일을 기록한다.
5. **포맷을 한 가지로 합치지 않는다.** 포맷마다 시간 기저, 구조, 채보 단위가 다르다. 대응 관계는 기록하되 통합은 근거가 쌓인 뒤에 한다.
6. **작성물마다 라이선스를 적용한다.** 명시하지 않으면 문서와 스키마는 CC BY-SA 4.0, 프로그램 코드는 GNU GPL v3.0이다.

## 범위 (제안)

| 포함 | 제외(지금은) |
| --- | --- |
| 채보와 곡 메타데이터, 딸린 음원·이미지·영상의 참조와 식별 | 게임 플레이어나 에디터의 구현(구동기를 추가하는 대신 구현을 보고 정리한다) |
| 묶음 단위의 관리, 공유, 보존, 검증 | 저작물 자체의 호스팅과 재배포 권리 판단 |
| 텍스트로 파싱할 수 있고 명세나 소스가 공개된 포맷 | 명세가 없는 바이너리·비공개 포맷의 역공학 |
| 리플레이, 스토리보드 같은 부가 매체는 이후 단계에서 검토 | 포맷 사이의 자동 변환 |

## 열린 결정

아래는 이 정의를 확정하기 위해 정해야 할 것들이다. 현재 문서는 괄호 안의 안을 가정했다.

1. "매체"의 범위: 채보와 딸린 파일까지만(가정), 리플레이·스토리보드·스킨까지 넣을지.
2. 보존의 수준: 원본 파일 그대로 보관하고 식별한다(가정), 열람 가능한 정규화된 사본까지 만들지.
3. 공유의 방식: IPFS/kubo, iroh, 또는 둘의 병행. 현재는 [기술 채택 판단](crate::docs::adoption)에서 시험 후 채택으로 둔 상태다.
4. 저작권과 재배포: 도구가 어디까지 책임질지. 조사하지 못했다.
5. 변환의 포함 여부: 포맷 사이의 변환을 이 프로젝트의 목표에 둘지(가정은 제외).

## 읽는 법

확인 상태 표기는 모든 문서에서 같다.

| 표기 | 뜻 |
| --- | --- |
| 확인 | 원문을 직접 열어 확인함 |
| 부분 | 일부만 읽었거나 요약 도구의 결과에 기댄 것 |
| 미확인 | 근거를 찾지 못했거나 열지 못함 |

판정 용어는 **채택**, **시험 후 채택**, **보류**, **회피** 네 가지다.

- 버전, 날짜, 라이선스는 조사 시점의 값이다. 채택 전에 다시 확인해야 한다.
- "문서에 없다"는 말은 "존재하지 않는다"가 아니라 "그 문서에서 찾지 못했다"는 뜻이다.
- 법률 자문이 아니다. 라이선스 항목은 호환 여부를 조사한 메모일 뿐이다.

## 문서 만들기

```text
cargo doc --no-deps --open
```

- 마크다운 원본은 `docs/`에 있고 `src/docs.rs`가 `include_str!`로 rustdoc에 싣는다.
- 새 문서를 추가하려면 `docs/`에 마크다운을 만들고 `src/docs.rs`에 `pub mod`를 하나 추가한다.
- 코드 블록에는 언어(`text`, `abnf`, `sql` 등)를 적는다. 생략하면 rustdoc이 Rust 코드로 취급한다.
- 대괄호 표기(예: 인덱스 범위)는 백틱으로 감싼다. 그대로 두면 rustdoc이 링크로 해석하려 한다.
