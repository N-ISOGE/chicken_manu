# chicken_manu (치킨메뉴)

리듬게임·음악게임의 **매체**(플레이를 규정하는 채보 등)가 어떤 형식으로 존재하는지 조사하고,
그 매체를 **공유하고 보존**하기 위한 데이터 포맷, 스키마, 도구를 명세하고 구현한다.

## 용어: 매체와 에셋

- **매체**: 리듬게임·음악게임의 플레이를 규정하는 데이터. chart, 譜面, 보면, beatmap, simfile, level 등 출처마다 이름이 다르다.
- **에셋**: 매체가 **참조하는** 파일. 음원, 키음, 이미지, 영상 등이다. 에셋은 매체에 속하지 않고 바깥에 있다.
- 매체와 에셋의 관계가 곧 **파일 참조**이고, 이 관계를 읽어 내는 것이 도구의 일이다.
- 매체의 구성과 형식은 나중에 정의한다. 그때 에스펜 올셋(Aarseth)과 고든 체레자의 사이버미디어 모델을 참조할 예정이다.
  이 문헌은 아직 확인하지 못했다(`미확인`). 이름의 표기도 사용자 기록 그대로 적었다.

## 목표

목표는 두 축이다. 두 축은 서로를 먹여 살린다.

### 1. 매체의 형식 조사

리듬게임·음악게임의 매체(chart, 譜面, 보면, beatmap, simfile, level 등)가
어떤 형식으로 존재하는지 **목록화하고 근거와 함께 기록**한다.

- 대상: BMS 계열, 기타 히어로 계열(`.chart`, `.mid`), osu!(`.osu`), StepMania(`.sm`, `.ssc`)를 비롯한 채보 전반과,
  이를 읽고 쓰는 구동기·에디터·파서, 그 형식을 설명하는 규격.
- 산출물: 포맷·명세 목록, 구현별 세부 문서, 비교표, 이론 문헌 목록.
- 방식: 평가나 통합에 앞서 **무엇이 존재하는지부터** 빠짐없이 기록한다. 출처마다 신빙성을 매기고 원어를 그대로 보존한다.
- 현황: BMS 계열이 가장 깊이 조사돼 있다. 다른 계열은 주소와 대략적인 평가만 있었고, 2026-10-09에 별도 조사가
  상용 포맷, 에디터, 엔진·파서·변환기, 포맷별 채보 단위를 확인한 결과를 [지원 대상](crate::docs::formats)과 [참고 자료](crate::docs::references)에 옮겼다. 별도 조사 결과이고 이 저장소가 다시 확인한 값은 아니다.

### 2. 공유·보존 도구의 명세와 구현

조사한 매체를 **잃지 않고 옮기고 찾을 수 있게** 하는 규칙과 도구를 만든다.

- 명세: 매체와 매체가 참조하는 에셋을 한 묶음으로 설명하는 메타데이터 스키마와 데이터 포맷.
  묶음(binder), 패턴(채보), 파일, 제작 참여자(명의), 파일 식별(해시, IPFS CID), 파일 참조를 다룬다.
  로드맵상 METS에서 파생한 UTF-8 XML 스키마를 목표로 하고, 형식을 직접 만들기보다 **표준을 따른다**.
  보존에 필요한 메타데이터는 표준을 기준으로 파악한다.
- 구현: Rust 기반 도구. 채보 파일을 읽어 메타데이터와 파일 참조를 뽑고, 해시와 CID를 계산해 기록하고, 묶음을 관리·공유·배포한다.
- 현황: MariaDB 스키마 설계서 2차(2024-12-19), BMS 문법 초안, 기술 채택 사전 조사까지 했다.
  BMS 파일 읽기와 해시·CID 계산의 초기 구현은 `src/main.rs`에 있다(일회용 확인 도구 수준).

### 두 축의 관계

- 1축의 결과가 2축의 **요구사항**이 된다. 어떤 포맷을 최소한 지원할지, 파일 참조를 어떻게 해석할지,
  채보 하나가 파일 하나인지 여러 개인지가 스키마를 정한다.
- 2축의 필요가 1축의 **조사 질문**을 정한다. 다음 질문(파일 참조, 경로, 인코딩, 채보 단위, 묶음 단위, 식별)이
  스키마에 필요한 것들이다.
- 이 순서가 깨지지 않도록, 포맷을 스키마에 넣기 전에 해당 포맷의 세부 문서가 먼저 있어야 한다.

## 원칙

1. **원문을 기준으로 반영한다.** 출처의 표기와 용어를 그대로 두고, 통일이나 대응은 따로 기록한다.
2. **근거 없이 쓰지 않는다.** 확인하지 못한 값은 `미확인`으로 두고, 신빙성(A/B/C/X)과 확인 상태를 분리해 적는다.
3. **원본을 바꾸지 않는다.** 식별은 디코딩 전의 원시 바이트에서 계산한 해시로 한다.
4. **재현할 수 있어야 한다.** 같은 입력이 같은 식별자를 만들도록, 해시 알고리즘과 CID 생성 프로파일을 기록한다.
5. **포맷을 한 가지로 합치지 않는다.** 포맷마다 시간 기저, 구조, 채보 단위가 다르다. 대응 관계는 기록하되 통합은 근거가 쌓인 뒤에 한다.
6. **작성물마다 라이선스를 적용한다.** 명시하지 않으면 문서와 스키마는 CC BY-SA 4.0, 프로그램 코드는 GNU GPL v3.0이다.

## 열린 결정

아래는 이 정의를 확정하기 위해 정해야 할 것들이다. 사용자가 방향을 밝힌 상태이고, 1번과 4번은 따로 조사한 뒤 정한다.

1. "매체"의 범위와 구성: 구체적으로 정의해야 할 사항이다.
   이 문서는 에셋을 매체에서 제외했다. 리플레이·스토리보드·스킨을 매체로 볼지는 그 정의에서 정한다.
2. 보존의 수준: 도서관이 하듯 **목록(카탈로그)으로 관리하고 서로 공유**할 수 있는 도구를 목표로 한다.
   구체적으로는 더 봐야 하고, 우선 p2p망을 전제로 "열람만" 가능하게 할 수 있는지를 따로 조사한다.
   열람용 정규화 사본을 만들지는 그 결과를 보고 검토한다.
3. 공유의 방식: 처음에는 Rust에서 libp2p로 IPFS를 쓰려고 했다.
   기술 채택을 판단할 조사가 더 필요하다(libp2p 직접 사용의 가능성은 위 2번의 조사가 다룬다). 현재 상태는 [기술 채택 판단](crate::docs::adoption)에 있다(IPFS/kubo, iroh를 시험 후 채택으로 둠).
4. 저작권과 재배포: 도구가 어디까지 책임질지. 조건의 내용은 아직 조사하지 못했고, 따로 검토한다.
   별도 조사(재배포 조건 사실수집)가 BMS 행사 규약, osu! 정책, 법령의 원문 위치를 모았다([참고 자료](crate::docs::references::preservation) 2절). 조항 내용은 요약되지 않았다.
5. 포맷 사이의 변환: 나중에 다룬다. 지금은 매체의 명세와 보존이 먼저다.

## 읽는 법

확인 상태 표기는 모든 문서에서 같다.

| 표기   | 뜻                                         |
| ------ | ------------------------------------------ |
| 확인   | 원문을 직접 열어 확인함                    |
| 부분   | 일부만 읽었거나 요약 도구의 결과에 기댄 것 |
| 미확인 | 근거를 찾지 못했거나 열지 못함             |

판정 용어는 **채택**, **시험 후 채택**, **보류**, **회피** 네 가지다.

- 버전, 날짜, 라이선스는 조사 시점의 값이다. 채택 전에 다시 확인해야 한다.
- "문서에 없다"는 말은 "존재하지 않는다"가 아니라 "그 문서에서 찾지 못했다"는 뜻이다.
- 법률 자문이 아니다. 라이선스 항목은 호환 여부를 조사한 메모일 뿐이다.

## 문서 만들기

```text
cargo doc --no-deps --open
```

- 마크다운 원본은 `docs/`에 있고 `src/docs.rs`가 `include_str!`로 rustdoc에 싣는다.
- 새 문서를 추가하려면 `docs/`에 마크다운을 만들고 `src/docs.rs`에 `pub mod`를 하나 추가한다.
- 코드 블록에는 언어(`text`, `abnf`, `sql` 등)를 적는다. 생략하면 rustdoc이 Rust 코드로 취급한다.
- 대괄호 표기(예: 인덱스 범위)는 백틱으로 감싼다. 그대로 두면 rustdoc이 링크로 해석하려 한다.
