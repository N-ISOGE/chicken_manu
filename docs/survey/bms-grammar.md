# BMS 문법

[← 길라잡이][project-guide]

BMS 계열 파일의 텍스트 구조를 살펴보고 파서의 수용 범위를 비교하기 위한 문법 초안입니다. 공식 명세나 모든 구동기의 공통 동작을 정의하는 문서는 아닙니다. BMS 계열 이외의 형식은 [조사 대상 파악][nav-1]에서 다룹니다.

## 1. 문법 원문과 목적

| 문법 | 원문                    | 목적                                                                  |
| ---- | ----------------------- | --------------------------------------------------------------------- |
| ABNF | [bms.abnf][abnf-source] | 한 줄의 분류와 알려진 명령의 구문 검사, 별도 토큰 열의 블록 균형 검사 |
| EBNF | [bms.ebnf][ebnf-source] | 선택한 명령과 제어 블록을 파일 구조로 표현한 별도 초안                |

두 파일은 같은 문법의 기계적 변환본이 아닙니다. 문법 표기법뿐 아니라 허용하는 명령·값·확장이 다릅니다. 사용하려는 시작 규칙과 아래 차이를 먼저 확인합니다.

근거 자료는 [hitkey BMS command memo](https://hitkey.bms.ms/cmds.htm), [BM98 형식 문서](https://bm98.yaneu.com/bm98/bmsformat.html), [BMS 파서 구현 정리][parsers]입니다. 문법의 선택과 실제 구현에서 관찰한 동작을 구별하며, 원자료의 위치와 확인 범위는 [BMS 참고 자료][nav-3]에서 이어 볼 수 있습니다.

## 2. 문법에 넣기 전의 입력 처리

두 초안은 **디코딩된 텍스트**를 입력으로 사용합니다. 바이트 인코딩 판별, BOM 처리, `#CHARSET` 적용 여부와 우선순위는 대상 구현에서 따로 확인합니다. 문법만으로 인코딩을 고르거나 파일을 유효하다고 판단할 수 없습니다.

원본 바이트와 디코딩한 텍스트를 구별해 보존합니다. 검색·표시를 위한 정규화, 경로 보정, 확장자 대체도 원문을 덮어쓰는 처리와 구분합니다.

- ABNF의 줄 규칙에는 줄 구분자를 전달하지 않습니다. CRLF·CR·LF로 줄을 나누는 처리는 호출 측에서 수행합니다.
- EBNF는 줄 구분자를 포함한 파일 구조를 읽습니다. 파일 끝에 CR 또는 LF가 없으면 인식 검사 전에 LF 하나를 덧붙입니다. 이는 이 초안의 검사 절차이며 원본 파일에 끝 줄바꿈을 요구하는 규칙이 아닙니다.
- 제3자 자료·컨테이너 메타데이터를 채보 확장자만 보고 BMS로 분류하지 않습니다.

## 3. ABNF의 시작 규칙

### 줄의 분류와 엄격한 명령 검사

| 시작 규칙            | 읽는 범위                                                               |
| -------------------- | ----------------------------------------------------------------------- |
| `source-line`        | 알려진 명령, 일반 헤더, `%URL`·`%EMAIL`, 무시할 줄을 분류하는 관대 규칙 |
| `known-command-line` | 문법이 나열한 명령과 그 값 형식만 허용하는 엄격 규칙                    |

예를 들어 `#TOTAL invalid`는 일반 헤더로 보존할 수 있으므로 `source-line`에서 수용됩니다. 숫자 값을 요구하는 `known-command-line`에서는 거부됩니다. 관대 규칙을 사용하는 도구는 알려진 이름이 일반 헤더로만 맞았는지 진단해야 합니다. 수용 여부만으로 값이 올바르다고 판단하지 않습니다.

ABNF의 따옴표 문자열은 [RFC 5234](https://www.rfc-editor.org/rfc/rfc5234#section-2.3)에 따라 기본적으로 대소문자를 구별하지 않습니다. 이 성질을 명령 이름에 사용하지만 원문 값과 경로를 대문자화하지는 않습니다.

### 채널의 값 형식

| 채널                 | 구문상 값                       |
| -------------------- | ------------------------------- |
| `02`                 | 마디 길이를 나타내는 소수       |
| `03`                 | 두 자리 16진수의 나열           |
| 그 밖의 두 자리 채널 | 두 자리 base36 객체 참조의 나열 |

`#00102:.25`와 `#00103:FF`는 수용하지만, `#00102:ZZ`·`#00103:GG`·`#00111:1.5`는 채널 문법에서 거부합니다. 채널 `08`·`09`의 값은 BPM·STOP 슬롯을 참조하는 객체형 값으로 다룹니다. 참조하는 슬롯이 존재하는지와 실제 재생 시간은 의미 처리의 문제입니다.

### 블록 구조

`structure`는 원문 파일이 아니라 줄마다 만든 토큰 열을 입력으로 받습니다. 각 토큰 뒤에 공백 하나를 붙이며, 제어 줄이 아닌 줄은 `L`로 나타냅니다. 예를 들어 `RANDOM IF L ENDIF `는 수용됩니다.

이 층은 IF·SWITCH 계열의 균형과 중첩을 검사합니다. `ENDRANDOM`은 선택으로 취급합니다. 난수의 범위, 분기의 실행 결과, CASE 값의 타당성은 검사하지 않습니다. 첫 층의 잘못된 제어 명령을 일반 헤더로 넘긴 경우에는 구조 검사 전에 별도로 진단해야 합니다.

## 4. EBNF와의 차이

EBNF는 W3C XML 표기법을 사용하며 알려진 명령의 파일 구조를 표현합니다. 다음 차이는 의도적으로 남아 있어 두 초안의 수용 집합이 같다고 주장하지 않습니다.

| 항목           | ABNF 초안                              | EBNF 초안                                                    |
| -------------- | -------------------------------------- | ------------------------------------------------------------ |
| 명령 이름      | 따옴표 문자열은 대소문자 무관          | 대문자 리터럴을 사용하며 소문자 명령은 수용하지 않음         |
| 모르는 헤더    | 일반 헤더로 보존                       | 선택한 헤더만 수용                                           |
| 빈 텍스트 헤더 | `#TITLE`처럼 구분자 없는 빈 값도 수용  | 텍스트 헤더에 구분자 필요                                    |
| 숫자 범위      | 일부 규칙은 부호 있는 수를 구문상 허용 | BPM·마디 길이 등은 비음수 문법, 양수 여부는 별도             |
| 확장 주석      | 별도 전처리·정책의 문제                | `//`, `;`, 블록 주석을 파일 문법에 포함                      |
| 제어 구조      | 토큰 열의 중첩 검사                    | 파일 구조로 표현하며 RANDOM·SWITCH 본문의 중첩 범위가 제한됨 |
| 확장 헤더      | 알려진 목록 밖이면 일반 헤더로 보존    | `SCROLL` 등 별도로 나열한 확장 포함                          |

EBNF도 채널 `02`·`03`·그 밖의 채널을 서로 다른 값 규칙에 연결합니다. 경로의 공백은 보존하며, 경로의 유효성이나 플랫폼별 금지 문자는 이 문법에서 판정하지 않습니다.

## 5. 문법이 정하지 않는 것

다음은 대상 명세·구동기·파서와 함께 확인해야 합니다.

- 인코딩 판별과 선언·BOM·기본값의 관계
- 중복 헤더 처리와 같은 마디·채널의 병합
- 분기 선택과 같은 파일에서 생기는 서로 다른 해석 결과
- 36진·62진 인덱스와 대소문자 구분
- 파일 참조의 경로 기준, 확장자 대체, 누락 자료 처리
- 값의 의미상 범위, 시간 계산, 프로그램의 오류 복구

이 선택은 [스키마와 식별자][nav-2]에서 다룰 기록 단위에도 영향을 줍니다. 문법에 맞는 것과 실행 가능한 매체인 것은 구별합니다.

## 6. 재현 가능한 합성 검사

저장소 루트에서 다음과 같이 검사할 수 있습니다.

```sh
python -m pip install abnf==2.9.0 lark==1.2.2
python tools/check_bms_grammars.py
```

[검사 도구][grammar-check]는 ABNF를 `abnf`로 읽고, EBNF의 규칙을 Lark 표기로 옮겨 Earley 파서로 인식합니다. EBNF 변환기는 이 파일에서 사용하는 W3C 표기만 지원하며 범용 W3C 도구는 아닙니다. 두 검사 모두 전체 입력을 소비해야 통과합니다.

합성 검사 59건은 채널별 값·홀수 길이·공백 경로·빈 채널·일반 헤더·대소문자·줄 경계·끝 줄바꿈·제어 블록을 포함합니다. 두 문법이 의도적으로 다른 경우에는 각각의 기대값을 사용합니다. 이 결과는 모든 명령의 검증이나 모든 실제 BMS의 호환성을 증명하지 않습니다.

과거 실제 파일을 이용한 검사와 이번 합성 검사는 구분합니다. 현재 문법에 대해 실제 파일 집합의 전수 검사나 게임 실행은 다시 수행하지 않았습니다. 제3자 샘플은 이 검사 도구에 포함하지 않습니다.
