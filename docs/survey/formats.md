## 1. 무엇을 조사하는가

리듬게임·음악게임의 매체는 채보 파일 하나로만 이루어지지 않습니다. 하나의 파일에 여러 채보가 담기기도 하고, 채보와 곡 정보·음원·이미지가 여러 파일로 나뉘기도 합니다. 이 자료를 목록화하고 공유·보존하려면 어떤 형식이 존재하고, 각 형식이 자료를 어떻게 구성하고 연결하는지 먼저 파악해야 합니다.

이 문서는 조사할 대상과 형식별로 살펴볼 질문을 안내합니다. 개별 형식의 세부 규칙과 확인 근거는 연결된 상세 문서에서 다룹니다.

조사 대상은 리듬게임·음악게임에서 행위를 매개하는 매체의 형식입니다. BMS 계열, osu!, StepMania, 기타 히어로 계열 등이 여기에 포함됩니다. 형식을 설명하는 명세와 이를 읽고 쓰는 구동기·에디터·파서도 함께 살펴봅니다.

| 대상             | 살펴볼 내용                                                  |
| ---------------- | ------------------------------------------------------------ |
| 매체의 형식      | 이름, 확장자, 버전, 변종, 파일 구조와 해석 규칙              |
| 매체를 담는 묶음 | 폴더·압축 파일·컨테이너의 구성과 채보의 포함 관계            |
| 관련 자료        | 음원·이미지·영상·곡 정보의 위치, 참조 방식, 식별·권리 정보   |
| 명세와 구현체    | 형식을 설명하는 문서와 실제로 읽고 쓰는 프로그램의 처리 방식 |

리플레이·스코어·스킨은 현재 조사 범위에서 제외합니다. 음원·이미지·영상은 매체와 연결되는 관련 자료로 다룹니다.

## 2. 어떤 형식을 살펴보는가

### 발견 목록과 상세 조사 순서

발견 목록은 어떤 형식이 존재하며 그 근거가 무엇인지 기록합니다. 상세 조사에서는 그 형식의 구조와 해석 규칙을 확인합니다. 두 작업은 접근할 수 있는 자료의 조건에 따라 나누어 진행합니다.

| 구분           | 기록하거나 판단할 내용                                         |
| -------------- | -------------------------------------------------------------- |
| 발견 목록      | 형식의 이름·판본·관련 게임과 도구, 존재를 뒷받침하는 공개 근거 |
| 상세 조사 순서 | 공개 명세·읽을 수 있는 구현체·검증 자료의 유무와 접근 가능성   |

존재가 확인된 형식은 바이너리 여부나 명세의 공개 여부와 관계없이 발견 목록에 남깁니다. 공개 명세 또는 읽을 수 있는 구현체가 있는 대상부터 구조와 규칙을 상세 조사합니다. 근거에 접근할 수 없는 대상은 **미확인·후순위**로 표시하고, 무엇을 확인하지 못했는지 남깁니다. 명세를 읽지 못했다는 사실을 형식이 존재하지 않는다는 근거로 삼지 않습니다.

게임·도구 이름만 알려져 있고 구체적인 형식의 존재 근거를 확보하지 못했다면 **형식 미확인**으로 구분합니다. 이렇게 발견 상태와 조사 조건을 구별하는 것은 목록의 기록 방법을 정리하는 것이며, 프로젝트의 대상 범위나 도구 지원을 새로 확정하지 않습니다.

### 형식과 관련 자료의 예

다음은 조사 대상의 예입니다. 목록에 있다는 사실이 개별 형식의 존재 근거 확보, 도구의 지원 또는 검증 완료를 뜻하지는 않습니다. 확장자는 대상을 찾는 단서이며, 구체적인 형식과 판본은 명세·파일 내용·구현체를 함께 보고 구별합니다.

| 대상                     | 형식·파일의 예                              | 함께 살펴볼 자료                      |
| ------------------------ | ------------------------------------------- | ------------------------------------- |
| BMS 계열                 | `.bms`, `.bme`, `.bml`, `.pms`              | BMS 문서, 문법, 파서 구현             |
| bmson                    | `.bmson`                                    | 명세, 스키마, 판본과 확장             |
| StepMania                | `.sm`, `.ssc`                               | 곡·채보 구성, 로더 구현               |
| osu!                     | `.osu`, `.osz`                              | 모드별 채보 표현, 곡 묶음과 관련 파일 |
| 기타 히어로 계열         | `.chart`, `.mid`, `song.ini`, `.sng`        | 채보·트랙·난이도와 곡 정보의 관계     |
| DTX                      | `.dtx`                                      | 형식 문서, 관련 자료와의 연결         |
| 그 밖의 형식             | Quaver, KSH/KSON, UltraStar, DWI, KSF 등    | 각 형식의 명세와 구현체               |
| 상용·모바일·VR 등의 형식 | 아케이드 게임, Beat Saber, ADOFAI 등의 매체 | 공개 문서, 파서·변환기, 형식별 제약   |

상용·모바일·VR 등의 구체적인 후보는 [별도 문서][nav-4]에서 살펴볼 수 있습니다.

공개 명세가 있는 형식부터 살펴보면 구조와 파일 참조를 대조하기 쉽습니다. 명세를 찾지 못한 형식은 파서·변환기 같은 구현체를 근거로 살펴볼 수 있지만, 그 구현에서 관찰한 동작과 형식 전체의 규칙을 구분해야 합니다. 텍스트·바이너리 여부, 명세 공개 여부, 자료 확보 여부는 각각 기록합니다.

## 3. 형식마다 무엇을 확인하는가

형식 이름과 확장자를 모은 다음에는 채보·파일·묶음의 관계를 확인합니다. 이 관계가 달라지면 목록에 기록할 단위와 자료를 옮길 때 유지해야 하는 연결도 달라집니다.

| 질문                                  | 확인할 내용                                                           | 목록화·보존과의 관계                             |
| ------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------ |
| 무엇이 하나의 채보인가?               | 파일당 채보 수, 난이도·트랙·모드의 구별, 파일 안에서 채보를 찾는 방법 | 파일과 채보를 구별해 기록할 수 있는가            |
| 무엇이 하나의 묶음인가?               | 곡 폴더, 압축 파일, 컨테이너의 구성과 포함 관계                       | 함께 유지하고 옮겨야 할 범위는 어디까지인가      |
| 다른 자료를 어떻게 찾는가?            | 참조 필드, 상대 경로의 기준, 파일명 관행, 누락된 참조                 | 이동 후에도 자료 사이의 연결을 유지할 수 있는가  |
| 같은 이름의 형식을 어떻게 구별하는가? | 버전, 변종, 프로그램별 확장과 해석 차이                               | 식별자와 지원 범위를 어느 수준으로 구분할 것인가 |
| 내용을 어떻게 해석하는가?             | 문자 인코딩, 시간·위치 표현, 분기, 기본값, 오류 처리                  | 원문과 해석 결과를 어떻게 함께 기록할 것인가     |
| 어떤 근거로 확인했는가?               | 명세의 절·필드, 소스의 판본·위치, 실행 조건과 결과                    | 다른 사람이 같은 근거를 찾아 대조할 수 있는가    |

예를 들어 `.sm`·`.ssc`·`.chart`처럼 한 파일에 여러 채보를 담는 형식에서는 파일 하나를 채보 하나로 간주할 수 없습니다. 곡 정보가 별도 파일에 있는 경우에는 채보 파일만으로 묶음의 정보를 파악하기도 어렵습니다. 구체적인 사례와 확인 범위는 [포맷별 채보 단위와 파일 참조 필드][nav-6]에서 설명합니다.

이 조사 결과는 [스키마][nav-1]에서 다룰 기록 단위와 식별 방식을 검토하는 근거가 됩니다. 형식의 이름, 버전, 묶음 컨테이너, 변종을 어떻게 구별할지도 함께 검토합니다.

## 4. 명세는 어떤 형태로 기술되는가

형식을 설명하는 자료에는 자연어 문서, 형식 문법, 스키마, 실행 명세, 구현 코드가 있습니다. 이 자료들은 서로 다른 측면을 보여 줍니다. 문법·스키마가 표현하는 범위와 프로그램이 실제로 처리하는 범위를 함께 확인합니다.

| 자료                                                                                        | 살펴볼 내용                                                                                                                          |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| [bmspec](https://github.com/bemusic/bmspec)                                                 | Gherkin으로 기술한 BMS 실행 명세. README만 확인했으며, 공식 명세가 아님을 밝히고 있습니다. 개별 사례의 내용은 추가 확인이 필요합니다 |
| [bmson 명세](https://bmson-spec.readthedocs.io/en/master/doc/index.html)                    | Web IDL로 기술한 구조와 자연어 설명, 판본별 규칙                                                                                     |
| [bmson-schema](https://github.com/JLChnToZ/bmson-schema)                                    | bmson 명세와 별도로 제공되는 스키마 후보. 본문·대상 판본·적용 범위는 미확인입니다                                                    |
| [memon](https://github.com/Stepland/memon), [rd-schema](https://github.com/0f-0b/rd-schema) | JSON Schema 조사 후보. 스키마 본문과 표현하는 구조·제약은 미확인입니다                                                               |
| [RFC 5234](https://www.rfc-editor.org/rfc/rfc5234)                                          | 형식 문법을 작성하는 표기법인 ABNF                                                                                                   |

링크는 살펴볼 자료의 위치를 안내합니다. 스키마나 문법의 존재만으로 특정 판본의 모든 규칙이 표현되거나 검증됐다고 판단하지 않습니다.

이 저장소의 BMS 문법 초안과 ABNF·EBNF 표기, 검증 범위는 [BMS 문법][nav-5]에서 다룹니다. 프로그램별 해석 방식은 [BMS 파서 구현 정리][nav-3]에서 살펴볼 수 있습니다.

## 5. 조사 결과를 읽고 이어가기

조사는 평가·통합에 앞서 무엇이 존재하는지 목록화하는 데서 시작합니다. 공개 출처와 원어 표기를 보존하고, 확인한 판본과 적용 범위를 함께 적습니다. 자동 생성 문서나 근거가 불분명한 요약을 확정 근거로 사용하지 않습니다.

명세를 읽은 것, 소스를 대조한 것, 프로그램을 실행한 것은 서로 다른 확인입니다. 상세 문서에서는 출처·확인 시점·판본과 미확인 사항을 함께 살펴보아야 합니다. 다른 구현이나 판본에도 같은 규칙이 적용되는지는 별도로 확인합니다.
