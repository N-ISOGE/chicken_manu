## 작업 방식

### Git

- 브랜치는 `main`과 `dev` 두 개를 기본으로 한다.
  - `main`: 기본 브랜치이자 배포용. 직접 푸시할 수 없고 PR로만 바뀐다. `dev`에서 정리된 내용을 PR로 반영한다.
  - `dev`: 개발 통합용. 직접 푸시할 수 없고 PR로만 바뀐다.
- 작업은 `dev`에서 딴 **짧게 쓰고 지우는 브랜치**에서 하고, 끝나면 PR로 `dev`에 넣는다.
  - GitHub는 PR의 대상 브랜치(base)를 기본 브랜치인 `main`으로 잡는다. PR을 만들 때 base가 `dev`인지 확인한다.
  - 병합한 작업 브랜치는 지운다.
- 오래된 브랜치(`util-for-parsing`, `wrapper-bms-to-mets`, `add-reference`)는 이어 쓰지 않는다.
  내용은 PR로 `dev`에 들어가고, 그 뒤에 정리한다.

### 문서 나누기

나누는 기준은 줄 수나 용량이 아니라 **사람이 읽는 단위**, 곧 문단과 절, 문서의 구조다.

- 한 문서는 한 주제를 다룬다. 제목만 보고 무엇이 들어 있는지 짐작할 수 있어야 한다.
- 절 제목(목차)만 훑어서 찾는 내용의 위치를 알 수 있어야 한다. 그렇지 못하면 절의 순서를 고치거나 문서를 나눈다.
- 절 하나가 앞뒤 절을 읽지 않고도 읽히고, 다른 절과 읽는 목적이 다르면(예: 링크 모음과 판단 근거) 하위 문서로 뗀다.
- 서로 다른 주제의 표가 한 문서에 섞여 있거나, 표가 길어 한 화면에서 구조를 파악하기 어려우면 주제별로 나눈다.
- 같은 주제는 길어도 한 문서에 둔다. 흩어 두면 읽는 사람이 문서를 오가며 맥락을 이어야 한다.
- 나눈 하위 문서는 상위 문서의 목차를 거쳐 찾을 수 있어야 한다.

나누는 방법:

- 상위 문서(`docs/<이름>.md`)는 목차와 공통 설명만 남기고, 하위 문서는 `docs/<이름>/` 폴더에 둔다.
  예: `docs/references.md`와 `docs/references/`, `docs/formats.md`와 `docs/formats/`.
- 새 하위 문서는 `src/docs.rs`에서 상위 모듈 안의 모듈로 싣고(`crate::docs::references::bms`), 상위 문서와 `docs/index.md`의 목차에 넣는다.
  절 번호로 다른 문서를 가리킨 곳(`... N절`)이 있으면 함께 고친다.
- 이 기준은 이 저장소의 운영 결정이며, 외부 가이드라인과 대조해 확인한 것은 아니다. 크기는 나눌지 살펴보는 신호로만 쓴다.

### 마크다운 서식

- md는 prettier(3.3.3)로 맞춘다: `npx prettier@3.3.3 --write <파일>`.
- 전체를 한 번에 바꾸지 않고 **고치는 파일부터** 맞춘다. 서식 검사(`MARKDOWN_PRETTIER`)는 모든 파일이 맞춰질 때까지 워크플로에서 끈다.
- 아직 맞추지 않은 파일은 `npx prettier@3.3.3 --check "**/*.md"`로 볼 수 있다.
  맞춘 파일: `docs/bms-parsers.md`, `docs/references.md`, `docs/formats.md`, `docs/schema.md`, `docs/adoption.md`, `docs/bms-grammar.md`, `docs/index.md`, `docs/notes.md`, `docs/references/`와 `docs/formats/`의 하위 문서 전체.
